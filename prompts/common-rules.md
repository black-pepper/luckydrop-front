# Common Rules

프로젝트에서 AI 프롬프트를 만들거나 실행할 때 아래 규칙을 항상 따른다.

## Project Context
- 프로젝트는 `luckdrop-front` 프론트엔드 저장소다.
- `luckydrop-ui` 디렉터리는 실제 프론트엔드 앱에 포함되는 소스가 아니라, UI 시안 및 화면 제작만을 위한 별도 작업 폴더다.
- `luckydrop-ui`의 결과물을 실제 프론트엔드에 반영할 때는 필요한 파일과 변경사항만 선별해서 `luckdrop-front` 루트 앱에 적용한다.
- 기존 코드 구조와 디자인 시스템 구성을 우선 존중한다.
- 사용자 요청 범위를 벗어나는 확장 작업은 임의로 수행하지 않는다.

## Encoding
- 모든 파일은 항상 UTF-8로 저장한다.
- 문자열, 문서, 주석도 UTF-8 기준으로 유지한다.

## Working Rules
- 먼저 관련 파일과 흐름을 파악한 뒤 작업한다.
- 변경은 필요한 최소 범위로 수행한다.
- 기존 동작을 깨뜨릴 가능성이 있으면 영향 요소를 명시한다.
- 불필요한 대규모 리팩터링은 지양한다.
- AI가 버전이나 의존성을 임의로 선택하거나 고정하지 않는다.
- 버전 관련 변경이 필요하면 어떤 항목의 버전 조정이 필요한지 먼저 사용자에게 명확히 전달한다.

## Naming Rules
- 기존 프로젝트의 패키지, 디렉터리, 메서드, 변수 네이밍 패턴을 우선 따른다.
- 새 이름은 역할이 드러나게 짓고 과도한 축약은 피한다.
- 동일한 개념에는 같은 용어를 일관되게 사용한다.
- API, DTO, Service, Repository 이름은 현재 계층 구조와 책임이 드러나게 작성한다.
- 테스트 이름은 어떤 조건에서 무엇을 검증하는지 드러나게 작성한다.
- 프롬프트 문서 이름은 목적이 바로 보이도록 작성한다.

## Prompt File Naming
- 공통 규칙 문서: `common-rules.md`
- 목적별 문서: `development.md`, `verification.md`, `review.md`
- 초안 템플릿: `prompt-draft-template.md`
- 작업 프롬프트는 정렬이 쉽도록 숫자 접두어를 붙인다.
- 권장 형식은 `<nn>-<stage>-<type>-<task>.md` 이다.
- `nn`은 작업 순서를 나타내는 두 자리 숫자를 사용한다. 예: `01`, `02`, `03`
- `stage`는 `draft`, `approved`, `run` 중 하나를 사용한다.
- `type`은 `dev`, `verify`, `review` 중 하나를 사용한다.
- `task`는 작업 내용을 짧게 설명하는 영문 kebab-case를 사용한다.
- 예시: `01-draft-dev-draw-result-admin.md`
- 예시: `01-approved-dev-draw-result-admin.md`
- 예시: `01-run-dev-draw-result-admin.md`
- 같은 작업은 같은 번호를 유지하고 단계만 바꾼다.
- 파일명만 보고도 순서, 상태, 목적, 작업 내용을 이해할 수 있어야 한다.

## Communication Rules
- 설명은 짧고 명확하게 작성한다.
- 코드, 설계, 명명은 기존 프로젝트 스타일을 따른다.
- 확신이 없는 내용은 추정임을 분명히 밝힌다.

## Output Rules
- 무엇을 변경했는지 간단히 요약한다.
- 영향 범위와 확인이 필요한 부분이 있으면 함께 적는다.
- 테스트를 실행했으면 결과를 적고, 실행하지 못했으면 이유를 적는다.
